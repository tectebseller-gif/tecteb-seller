=== second pass — the one mutation that survived, and the two readings of
=== `database-all: 7` in the baseline above

⛔ TWO SEPARATE FINDINGS, and neither is a defect in the package.

(1) MUTATION 6 SURVIVED THE FIRST PASS, and it was a hole in MY OWN tests.
    «a page that came up short is reported as the whole page» removes

        if (count($rows) !== $expected) { return null; }

    from `DbProductRepository::reconciliationPage()`. Every test in
    `CatalogueReconciliationTest` read a HEALTHY database, where the count and
    the list always agree — so the guard was unreachable, and an unreachable
    guard is byte for byte indistinguishable from an absent one (`alpha.80`).

    Closed with a behavioural test that injects the refusal into the LIST
    statement by name and leaves the `COUNT(*)` beside it working, plus the
    control that the same call answers the whole page once the refusal stops:

        CatalogueReconciliationTest::testAPageWhoseRowsCouldNotBeReadIsNullRatherThanEmpty

    Re-measured on the quiet tree, mutation 6 alone:

        applied to src/Modules/Product/Infrastructure/DbProductRepository.php
        database (CatalogueReconciliationTest): 1 failure
        RESULT: falsified
        restored byte for byte: yes

    So: 14 mutations, 14 falsified — the fourteenth on the second pass.

(2) `database-all: 7` IN THE CLOSING BASELINE IS NOT A RESULT ABOUT THIS TREE.
    While that unfiltered run was in progress I started a SECOND database
    runner on the same database to check the new test. That is `alpha.40`'s
    collision, for the fourth time in this repository, and the answer belongs
    to neither tree.

    ⛔ And the reason I started it is worth writing down, because the check I
    used was wrong rather than missing: `pgrep -cf phpunit` answered `1` and I
    read that as «the loop is finished». One is not zero — it was the loop's
    own runner. The condition to wait on is `= 0` AND the log carrying its
    verdict, which is what the later wait actually did.

    The clean figures are in docs/TEST-EVIDENCE-ALPHA105-FA.md, measured with
    the database suite ALONE on the quiet tree, twice: once on PHP 8.3.6 and
    once on real PHP 8.1.34 in the container.

=== third finding, from the final measurement run: the figure that did not
=== repeat, and the two guards that earned their keep

(3) THE DATABASE SUITE'S ASSERTION COUNT DID NOT REPEAT, AND THE INTERPRETER
    IS NOT THE VARIABLE.

    first run on 8.3.6   : OK (1265 tests, 14498 assertions)
    second run on 8.3.6  : OK (1265 tests, 14494 assertions)  --log-junit
    run on real 8.1.34   : OK (1265 tests, 14494 assertions)  --log-junit

    The two logged runs were compared TEST BY TEST: 1265 tests on each side,
    14494 assertions on each side, and ZERO per-test difference. So the four
    assertions did not come from PHP 8.1 versus 8.3.

    The first run has no per-test log, so its test is NOT named here and NOT
    guessed at. What is on the record is this: those four assertions were in
    the run that started immediately after this falsification loop, whose own
    closing baseline was the two-runner collision recorded above; and this
    suite's shared setUp() truncates the options table, drops the audit table
    and resets postmeta, but does NOT truncate the plugin's own tables — each
    class resets what it needs. A row-conditional assertion in a class that
    does not reset can therefore move with what a previous run left behind.
    That is a statement about test isolation, not about the package, and it is
    written as an open observation rather than a cause.

    The figure carried into the documents is 14,494, because two independent
    measurements agree on it.
