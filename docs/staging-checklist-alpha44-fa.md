# چک‌لیست کوتاه آزمایش `0.1.0-alpha.44` روی staging

بسته: `tecteb-marketplace-core-0.1.0-alpha.44.zip` ·
`8d39f7cb954d62a47aeec52326c0a920522f85b718ee6433e02ef4f545bc2263`
نصب روی `staging.tecteb.com` **کار مالک است**؛ ما نصب نمی‌کنیم.

نصب فعلی staging روی **`alpha.40` / ساختار ۲۲** است، پس این ارتقا
**migration ۲۳ را اجرا می‌کند**. این دور **یک قاعده** را عوض کرده، پس
چک‌لیست هم کوتاه است: گام ۰ و گام ۱ مثل همیشه، و بعد **فقط گام ۲**.

---

## گام ۰ — پیش از هر کاری

- [ ] **پشتیبان دیتابیس**: `wp db export backup-before-alpha44.sql`
- [ ] **پشتیبان فایل‌ها**: حداقل `wp-content/plugins/` و `wp-content/uploads/`
- [ ] نسخه و ساختار فعلی را یادداشت کنید:
      `wp plugin get tecteb-marketplace-core --field=version` و
      `wp option get tmc_schema_version` → باید `0.1.0-alpha.40` و `22` باشد
- [ ] ترتیب پنج‌گامی توقف فروش: `docs/upgrade-and-rollback.md` بند ۵٫۲-ب

## گام ۱ — تعویض بسته

- [ ] افزونه را از wp-admin بارگذاری و «Replace current with uploaded» کنید
- [ ] **یک بار** یک صفحهٔ wp-admin را باز کنید (دروازهٔ ارتقا روی درخواست مدیر
      اجرا می‌شود، نه روی قلاب فعال‌سازی)
- [ ] `wp option get tmc_schema_version` → **۲۳**
- [ ] `wp plugin get tecteb-marketplace-core --field=version` → **`0.1.0-alpha.44`**
- [ ] `wp option get tmc_migration_error` → خالی

## گام ۲ — تنها چیزی که این دور عوض شده: ویرایش مدیر روی ویژگی‌ها

روی یک محصول بازارگاهی با **برند** و **دو مشخصهٔ پرشده** که تأیید شده است:

- [ ] صفحهٔ محصول → زبانهٔ **«اطلاعات بیشتر»**: برند و هر دو مشخصه، هرکدام
      **یک بار**، با برچسب فارسی و واحد چسبیده به مقدار.
- [ ] در wp-admin، مقدار **برند** را **با دست عوض کنید** و ذخیره کنید.
- [ ] از پنل فروشنده همان محصول را ذخیره یا تأیید کنید (بدون عوض‌کردن چیزی).
- [ ] **مقدار مدیر باید بماند.** این همان چیزی است که در `alpha.43` بی‌صدا
      پاک می‌شد.
- [ ] یک مشخصه را در «الگوی مشخصات» **بازنشسته** کنید:
      - اگر مدیر مقدارش را **عوض کرده بود** → باید **بماند**؛
      - اگر **دست‌نخورده** بود → باید **برود**.
- [ ] **برچسب** یک مشخصه را عوض کنید: اگر مدیر مقدار قبلی را عوض کرده بود،
      ردیف قدیمی **می‌ماند** (مال اوست) و ردیف تازه هم نوشته می‌شود — پس روی
      چنین محصولی دو ردیف می‌بینید و این **درست** است.
- [ ] ویژگی‌ای که مدیر **خودش** اضافه کرده (نامی که افزونه نمی‌نویسد) باید
      دست‌نخورده بماند.
- [ ] اگر خواستید افزونه دوباره مالک یک ویژگی شود: **در ووکامرس حذفش کنید**؛
      ذخیرهٔ بعدی فروشنده یکی تازه می‌نویسد که مالکش است.

### روی یک محصول متنوع

- [ ] گزینه‌های یک محور را در wp-admin **با دست** عوض کنید، بعد از پنل
      فروشنده ذخیره کنید → **مجموعهٔ مدیر باید بماند**.
- [ ] و روی محوری که مدیر دستش نزده، گزینهٔ تازهٔ فروشنده **باید اعمال شود**.
- [ ] **شناسهٔ تنوع‌ها، قیمت، موجودی و SKU نباید عوض شوند.**

## گام ۳ — اگر چیزی خراب بود: بازگشت

- [ ] بستهٔ `alpha.43` یا `alpha.40` را دوباره بارگذاری کنید.
      **بازیابی دیتابیس لازم نیست.**
- [ ] اثرهای بازگشت، با عدد و شاهد: `docs/upgrade-and-rollback.md` بند ۲۷٫۳.
      خلاصه: **ویرایش مدیر بازگشت را هم دوام می‌آورد** (اندازه‌گیری‌شده)، ولی
      نقصِ این دور برمی‌گردد و مشخصهٔ بازنشسته دیگر حذف نمی‌شود.

## آنچه این بسته **نمی‌کند**

- هیچ پیامک، ایمیل یا پرداختی نمی‌فرستد؛ `canTransferMoney()` در هر build
  `false` است.
- هیچ دروازهٔ سفارش، پرداخت یا تسویه‌ای باز نشده.
- **تأیید موبایل (OTP) انجام نمی‌شود.**
- متن توضیحات، تنظیمات فروشگاه، اعلان‌ها، منطق مالی، دکان و چرخهٔ تأیید
  **لمس نشدند**.
- **علتِ Request Timeout هنگام ساخت همچنان باز است** و هیچ ادعایی دربارهٔ
  رفعش اضافه نشده.

> **«آماده آزمایش روی staging» با «آمادگی سایت اصلی» یا «باز شدن فروش و
> پرداخت واقعی» یکی نیست.** جدول سه‌ستونه:
> `docs/phase-41-attribute-ownership-and-media.md` بند ۱۰.
