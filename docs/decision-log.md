# دفتر تصمیم‌ها — تصمیم‌های باز، وضعیت هر جزء و فرض‌های فنی فاز ۱

بازبینی ۴ · ۷ سپتامبر ۲۰۲۶ · پس از اجرای فاز ۱. تصمیم‌های باز تغییری نکرده‌اند؛ فقط اثر واقعی هر کدام روی کد ثبت شده است.

## ۴. سورس قبلی — وضعیت: تعیین‌نشده

### آنچه ثابت شده
مخزن `tectebseller-gif/tecteb-seller` در شروع این جلسه **صفر commit و هیچ
فایل** داشت. این فقط ثابت می‌کند که **در همین مخزن** سورسی وجود ندارد.
**اثبات نمی‌کند** که هیچ سورس قبلی در جای دیگری وجود ندارد. بازبینی ۱ این را
اشتباه به «هیچ سورس قبلی وجود ندارد» تعمیم داده بود؛ آن نتیجه پس گرفته شد.

### آنچه مالک گزارش کرده
سابقه یک اسکلت با نام فایل **`tecteb-marketplace-v0.1.1.zip`** وجود دارد.

| مورد | وضعیت |
|---|---|
| دریافت فایل در این جلسه | ❌ دریافت نشده |
| محتوا، ساختار، slug واقعی داخل ZIP | ❓ نامعلوم |
| نصب‌بودن روی سایت / Staging | ❓ نامعلوم |
| نسبت آن با `tecteb-marketplace-core` | ❓ نامعلوم |
| **وضعیت دریافت و استفاده** | **تعیین‌نشده** |

### آنچه از نام فایل *قابل استنباط* است (استنباط، نه واقعیت)
- slug ظاهری: `tecteb-marketplace` — با slug مصوب `tecteb-marketplace-core`
  متفاوت است.
- نسخه ظاهری: `0.1.1` — از `0.1.0-alpha.1` پیشنهادی بالاتر است.

### پیامدها تا تعیین تکلیف
1. فرض «هیچ سورس قبلی وجود ندارد» **قطعی نیست** و در هیچ سند دیگری به‌عنوان
   واقعیت نوشته نمی‌شود.
2. طبق پرامپت («اگر پروژه قبلی با slug متفاوت وجود دارد، یک افزونه رقیب
   هم‌نام نساز؛ نگاشت هویت و برنامه سازگاری را پیشنهاد بده و فقط تصمیم
   مربوط به آن را بپرس»)، پیش از **نصب** هر ZIP روی هر سایتی که ممکن است
   آن اسکلت روی آن باشد، نگاشت هویت لازم است. این مانع **scaffold** در
   مخزن نیست، ولی مانع ادعای «قابل نصب» هست.
3. F-01 (نسخه انتشار) به این تعیین تکلیف وابسته می‌شود (بند ۵).
4. **هیچ دستوری درباره اسکلت قبلی قطعی نیست** — نه «غیرفعال کن»، نه
   «کنار هم نگه دار»، نه «option/جدولش را مهاجرت بده». هر دستوری از این
   دست فقط **پس از** بررسی فقط‌خواندنی محتوا، وابستگی‌ها و وضعیت نصب آن
   قابل نوشتن است. بازبینی ۲ در گزینه م-۱ چنین دستوری را زودهنگام نوشته
   بود؛ پس گرفته شد.

### ترتیب تعیین تبار (وابسته به بررسی فقط‌خواندنی)

```
دریافت ZIP  →  بررسی فقط‌خواندنی (محتوا، وابستگی‌ها، وضعیت نصب)  →  تعیین تبار  →  نسخه انتشار
```

تعیین تبار **پیش از** بررسی فقط‌خواندنی انجام نمی‌شود. **فعلاً هیچ گزینه‌ای
انتخاب نشده است.**

### گزینه‌های تبار (برای تصمیم پس از بررسی؛ هیچ‌کدام انتخاب نشده)

| گزینه | معنی | اثر بر نسخه انتشار | اثر بر نصب |
|---|---|---|---|
| **م-۱: تبار جدا** | `tecteb-marketplace-core` محصول جدیدی است؛ اسکلت قبلی سلف آن نیست | الزام عقب‌نرفتن **ندارد** → `0.1.0-alpha.1` | رفتار با اسکلت قبلی پس از بررسی تعیین می‌شود؛ هیچ دستوری الان قطعی نیست |
| **م-۲: ادامه همان تبار (جانشین)** | افزونه جدید ادامه همان اسکلت است | الزام عقب‌نرفتن **دارد**: نه کمتر از `0.1.1`؛ پیشنهاد `0.2.0-alpha.1` | برنامه سازگاری داده/option/جدول پیش از فاز ۲؛ فقط پس از بررسی ZIP |
| **م-۳: دو افزونه مستقل، هم‌زیستی** | هر دو مستقل‌اند و مدتی کنار هم فعال می‌مانند | **به‌تنهایی الزام عقب‌نرفتن ندارد** → `0.1.0-alpha.1` مجاز | تضمین slug/prefix متفاوت؛ فهرست تداخل menu/option/capability پس از بررسی |

**تنها درخواست فعلی از مالک:** در اختیار گذاشتن `tecteb-marketplace-v0.1.1.zip`
برای بررسی فقط‌خواندنی. انتخاب م-۱/م-۲/م-۳ **پس از** آن بررسی انجام می‌شود، نه
الان. تا آن زمان وضعیت «تعیین‌نشده» می‌ماند و کار مستقل ادامه می‌یابد.

## ۵. فرض‌های فنی فاز ۱ — F-01 تا F-05

اینها **انتخاب فنی** هستند، نه قاعده تجاری. هرجا مرجع قراردادی دارند، ذکر
شده تا معلوم باشد چه چیزی «فرض» است و چه چیزی «الزام».

### F-01 — نسخه انتشار افزونه (مستقل از نسخه schema دیتابیس)

دو نسخه **مستقل** وجود دارد و نباید با هم مخلوط شوند:

| | نسخه انتشار افزونه | نسخه schema دیتابیس |
|---|---|---|
| شکل | رشته semver در header فایل main (مثل `0.1.0-alpha.1`) | عدد صحیح، شروع از `1` |
| محل تعریف | header فایل main + ثابت `PLUGIN_VERSION` | ثابت `SCHEMA_VERSION` در `src/Core/Migration/SchemaVersion.php` |
| محل ذخیره | فقط در کد (WordPress از header می‌خواند) | option `tmc_schema_version`، **فقط پس از migration موفق** |
| کِی تغییر می‌کند | هر انتشار | **فقط وقتی ساختار** (جدول، ستون، ایندکس، شکل option) تغییر می‌کند |
| مصرف‌کننده | کاربر، WordPress، پاسخ `plugin.version` در Health | فقط `MigrationRunner` |

**قاعده اجرای migration:** runner فقط وقتی `stored < SCHEMA_VERSION` است
مرحله‌های باقی‌مانده را اجرا می‌کند. ارتقای نسخه انتشار **بدون تغییر ساختار**
هیچ migrationی اجرا نمی‌کند و قفل migration را هم نمی‌گیرد. یک نسخه schema
می‌تواند چندین نسخه انتشار را پوشش دهد. در فاز ۱: `SCHEMA_VERSION = 1`
(ساخت جدول audit) — مستقل از این‌که نسخه انتشار چه باشد.

مقدار نسخه انتشار:

| | |
|---|---|
| مقدار | **وابسته به تعیین تبار (DEC-06-d)** که خودش وابسته به بررسی فقط‌خواندنی سورس قبلی است |
| مرجع الزام عقب‌نرفتن | پرامپت: «اگر نسخه قبلی وجود دارد، نسخه را عقب نبر.» — این الزام **فقط برای ادامه همان تبار** (م-۲) معنا دارد؛ دو افزونه مستقل (م-۱ یا م-۳) **به‌تنهایی** چنین الزامی ندارند |
| اگر م-۲ | نه کمتر از `0.1.1`؛ پیشنهاد `0.2.0-alpha.1` |
| اگر م-۱ یا م-۳ | `0.1.0-alpha.1` (قاعده مخزن خالی در پرامپت) |
| تا تعیین تبار | **هیچ گزینه‌ای انتخاب نشده.** اگر پیاده‌سازی پیش از تعیین تبار مجاز شود، header مقدار موقت `0.1.0-alpha.1` را **فقط به‌عنوان قاعده مخزن خالی پرامپت** با علامت TODO ارجاع به همین بند می‌گیرد؛ این مقدار موقت **انتخاب تبار نیست** و با م-۲ بالا می‌رود |
| اثر تغییر بعدی | فقط رشته header/`PLUGIN_VERSION`؛ نسخه schema و migration **دست نمی‌خورد** — دقیقاً به همین دلیل دو نسخه مستقل نگه داشته می‌شوند |
| اثبات استقلال | `MigrationRunnerTest::testReleaseUpgradeWithoutStructuralChangeRunsNothing` — ارتقای نسخه انتشار بدون تغییر ساختار هیچ migrationی اجرا نمی‌کند و قفل هم نمی‌گیرد |
