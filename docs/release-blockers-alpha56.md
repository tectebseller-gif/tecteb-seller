# فهرست مانع انتشار — `0.1.0-alpha.56`

این سند جواب بند ۱ دستور است: **برای هر قابلیت ضروری، یک وضعیت صریح**، خوانده
از خودِ کد و از شواهد اجرا — نه از فهرست کلاس‌ها.

> **وجود یک کلاس یا ماژول، قابلیت تمام‌شده نیست.** هر ردیف پایین به یک چیز
> قابل‌بررسی اشاره می‌کند: فایلی که تصمیم را می‌گیرد، سوییتی که اجرایش می‌کند،
> یا شاهدی که اندازه‌اش گرفته. جایی که هیچ‌کدام نیست، وضعیت «ساخته ولی
> آزموده‌نشده» است و همان نوشته شده.

## پنج وضعیت، و معنای دقیقشان

| وضعیت | معنا |
|---|---|
| **ساخته و آزموده‌شده** | کد هست، و یک سوییت یا شاهدِ اجرا **رفتارش** را می‌سنجد — نه فقط وجودش. |
| **ساخته ولی آزموده‌نشده** | کد هست و هیچ آزمونی مسیرش را **اجرا** نمی‌کند، یا تنها آزمونش دربارهٔ ثبت‌شدن است نه کارکردن. این یک مانع است. |
| **ناقص** | نیمی از کار هست. چیزی که لازم است و نوشته نشده، با نام. |
| **نیازمند تصمیم مالک** | کد منتظر یک جواب تجاری است و تا آن جواب، دروازه بسته است. حدس زده نمی‌شود. |
| **نیازمند شواهد سایت** | جواب فقط از دادهٔ خودِ `tecteb.com` یا `staging.tecteb.com` می‌آید و این مخزن به آن دسترسی ندارد. |

## آنچه از دکان **واقعاً استفاده می‌شود** — جدا از آنچه دکان می‌تواند بکند

دستور می‌گوید این دو را قاتی نکن. مبنا: سه فایل واقعی که مالک فشرده کرد
(`alpha.53`) و `tools/plugin-exit-inventory.php`.

**از فایل‌های تحویل‌شده اثبات‌پذیر است که بستهٔ Pro ناقص است:**
`includes/Module.php` خودش **۴۱ ماژول** می‌شناسد و `modules/` تنها **۱۰** پوشه
دارد. پس هر قابلیتی که در آن ۳۱ پوشهٔ غایب است، روی سایت مالک **اجرا نمی‌شود**
— و `vendor-staff` یکی از همان‌هاست.

| قابلیت دکان | روی سایت مالک | وضعیت بازسازی اینجا |
|---|---|---|
| فروشنده، پروفایل، وضعیت | استفاده می‌شود (جدول‌های Lite) | `ImportFromDokan` می‌خواند و نگاشت می‌کند — ساخته و آزموده‌شده |
| محصول فروشنده | استفاده می‌شود | همان مسیر؛ تعارض رد می‌شود |
| سفارش و زیرسفارش | استفاده می‌شود (`dokan_order_stats`) | **نیازمند شواهد سایت**: مرجع ۵٫x `dokan_order_stats` است نه `dokan_orders`، و ستون‌های پولش `double` اند. تغییر مرجع مبالغ بی تصمیم مالک انجام نشد. |
| برداشت و مانده | استفاده می‌شود | `ReconcileDokanFinance` دو ستون می‌دهد که **جمع نمی‌شوند** (دکان برداشتِ پرداخت‌شده را عمداً دوبار ثبت می‌کند) — ساخته و آزموده‌شده |
| **پرسنل فروشگاه** | **نامعلوم** | پوشهٔ `vendor-staff` در بستهٔ Pro نیست، و `_dokan_vendor_id` در ۵٫۱٫۱ متای **سفارش** است نه usermeta پرسنل. **نیازمند دادهٔ سایت**، نه حدس. |
| مرجوعی دکان | **نامعلوم** | ماژولش بین آن ۱۰ پوشه نیست. |
| صفحهٔ فروشگاه و rewrite | استفاده می‌شود | `alpha.16` سه حالت را اندازه گرفت؛ غیرفعال‌کردن دکان قاعده‌های rewrite اش را پاک نمی‌کند — **ساخته و آزموده‌شده، با هزینهٔ نوشته‌شده** |

## چهار مانعِ انتشار، به‌ترتیب اهمیت

1. **DEC-02…05 و درگاه پرداخت** — تصمیم مالک. تا آن وقت `OrderOperationsGate`
   هر فروشی را رد می‌کند و این **درست** است.
2. **`step_base_differs`** — مانع خروج Min Max برای هر محصولی که قاعده‌اش با
   مبنای گام ووکامرس نمی‌خواند. کد لازم نیست؛ تصمیم لازم است: کدام مجموعهٔ
   مجاز درست است.
3. **نسخه و کلیدهای دکان Pro و Lite، و پرسنل** — نیازمند شواهد سایت. بی آن،
   خروج دکان قابل اعلام نیست.
4. **PHP 8.1.34 واقعی، قالب واقعی، و کش شیءِ پایدار** — نیازمند شواهد سایت.
   هیچ‌کدام در این محیط اجرا نمی‌شود و هیچ‌کدام «قبول» اعلام نشده.
