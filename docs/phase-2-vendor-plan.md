## ۲. مدارک پویا — سازوکار جداست از فهرست

این تفکیک، محور اصلاح اول مالک است و در کد هم دو چیز جداست:

| لایه | چیست | چه کسی تعیین می‌کند | وضعیت امروز |
|---|---|---|---|
| **سازوکار** | فرم‌ساز مدارک: تعریف نوع مدرک، اجباری/اختیاری، فرمت‌های مجاز، بیشینه اندازه، اینکه به کدام نوع فروشنده و کدام دسته کالا اعمال شود، متن راهنما، و ترتیب نمایش | **ما می‌سازیم** | **مانعی ندارد؛ همین حالا قابل ساخت است** |
| **فهرست** | اینکه واقعاً کدام مدارک قانونی/پزشکی لازم است | **مالک/مدیر بازارگاه** در همان فرم‌ساز وارد می‌کند | **نامعلوم — و حدس زده نمی‌شود** |

هیچ مدرک قانونی یا پزشکی در کد، seed، مهاجرت یا متن پیش‌فرض نوشته نمی‌شود.
داده نمونه فقط در پیش‌نمایش است و برچسب «نمونه» دارد.

### ۲٫۱ سه وضعیت مجموعه‌الزامات، و رفتار صریح فرم

مجموعه‌الزامات مدارک (برای هر نوع فروشنده) دقیقاً یکی از این سه است:

| وضعیت | معنی | رفتار فرم درخواست |
|---|---|---|
| `undefined` (پیش‌فرض) | مدیر هنوز چیزی تعریف نکرده | پر کردن و **ذخیره پیش‌نویس آزاد**؛ «ارسال برای بررسی» **غیرفعال** با همین جمله که چرا؛ هیچ مدرکی خواسته نمی‌شود؛ **هیچ تأیید خودکاری رخ نمی‌دهد** |
| `configured` | دست‌کم یک نوع مدرک تعریف شده | مدارک اجباری باید بارگذاری شوند تا ارسال فعال شود |
| `explicitly_none` | مدیر **صریحاً** گفته این نوع فروشنده مدرکی لازم ندارد | ارسال فعال است؛ این تصمیم با نام مدیر و زمان در audit ثبت می‌شود |

تفاوت `undefined` و `explicitly_none` عمدی است: «هنوز تعیین نشده» هرگز به
معنی «لازم نیست» تفسیر نمی‌شود. تنها راه رسیدن به وضعیت دوم، یک تصمیم ثبت‌شده
مدیر است.

### ۲٫۲ آنچه نبودِ فهرست **مسدود نمی‌کند**

جدول‌ها و migrationها، فرم چندمرحله‌ای، ذخیره پیش‌نویس، پروفایل، پرسنل، صف
بررسی مدیر و خود فرم‌ساز — همه بدون فهرست ساخته و آزموده می‌شوند. صف بررسی
از روز اول درخواست‌های `submitted` را نشان می‌دهد؛ اگر هنوز هیچ درخواستی
ارسال‌شدنی نباشد، حالت خالی معنادار نمایش می‌دهد، نه صفحه خطا.

## ۳. ثبت‌نام و تأیید فروشنده

### ۳٫۱ مسیر (مادر ۴٫۱)

1. ثبت‌نام عادی **همیشه** حساب مشتری می‌سازد؛ فروشنده‌شدن یک درخواست جداست.
2. کاربر هم‌زمان یا بعداً فرم را پر می‌کند.
3. درخواست: اطلاعات حقوقی، تماس، نشانی، مدارک (طبق بند ۲) و پذیرش قوانین.
4. وضعیت‌ها: `draft`، `submitted`، `changes_requested`، `in_review`،
   `approved`، `rejected`، `suspended`.
5. **تأیید فروشنده و اجازه انتشار مستقیم محصول دو مجوز جدا هستند.**
6. هر تصمیم با مدیر، زمان، دلیل و تاریخچه ثبت می‌شود.

### ۳٫۲ نگاشت به کد

| چیز | تصمیم |
|---|---|
| موجودیت‌ها | `VendorProfile`، `VendorApplication`، `VendorDocumentType`، `VendorDocument`، `VendorStaffLink` (مادر ۱۱٫۱) |
| مالکیت داده | جدول‌های اختصاصی با پیشوند `tmc_`؛ هیچ داده فروشنده در postmeta ووکامرس (ARCH-01) |
| هویت کاربر | `vendor_profile.user_id` → `wp_users.ID`؛ وردپرس مالک هویت می‌ماند |
| ثبت تصمیم | همان `AuditRepositoryInterface` فاز ۱ (CORE-08) |
| مجوزها | `tmc_apply_vendor`، `tmc_review_vendor`، `tmc_sell`، `tmc_publish_product_directly`، `tmc_manage_vendor_documents` |
| گذار وضعیت | ماشین وضعیت صریح؛ گذار نامعتبر استثنا می‌دهد، نه ذخیره بی‌صدا |

## ۴. هویت: ثبت شماره ≠ تأیید شماره

### ۴٫۱ قاعده سخت

`mobile_verified_at` فقط و فقط وقتی مقدار می‌گیرد که **یکی از این دو** رخ داده
باشد:

1. یک `OtpProviderInterface` واقعی `verifyChallenge()` را با نتیجه `verified`
   برگردانده باشد؛ یا
2. یک اتصال **مستند** به سامانه ورود موجود، تأیید شماره را گواهی کند و آن سند
   در همین مخزن ثبت شده باشد.

تا هیچ‌کدام نباشد، شماره در وضعیت `registered_unverified` می‌ماند. هیچ مسیر
دیگری — نه تنظیم مدیر، نه seed، نه محیط توسعه — حق ساختن `verified` ندارد؛
آزمون این را اجرا می‌کند.

### ۴٫۲ تفکیک «کاربر واردشده» از «کاربر با موبایل تأییدشده»

| مفهوم | مالک | چطور خوانده می‌شود | چه چیزی را باز می‌کند |
|---|---|---|---|
| ورود به حساب | **وردپرس** (همان صفحه ورود فعلی) | `is_user_logged_in()` در لایه Adapter | دیدن داشبورد فروشنده در حد وضعیت درخواست |
| موبایل تأییدشده | افزونه | `VendorIdentity::isMobileVerified()` | کارهایی که سند آن‌ها را به هویت تأییدشده گره زده است |

ورود موجود **دروازه** است: افزونه `wp_signon`/`wp_set_auth_cookie` صدا نمی‌زند،
session نمی‌سازد و مسیر ورود جایگزین نمی‌سازد. آزمون بسته‌بندی امروز هم همین
را اجرا می‌کند. کاربری که وارد شده اما موبایلش تأیید نشده، **کاربر معتبر است**؛
فقط کارهای وابسته به هویت تأییدشده برایش باز نمی‌شود و دلیلش روی صفحه نوشته
می‌شود (تصویر پیش‌نمایش).

### ۴٫۳ فایل مرجع دروازه — درخواست مشخص

`tecteb-gateway-reference.zip` **در این مخزن نیست**. جست‌وجو شد:

```
find / -name "*gateway*reference*"        → چیزی نیست
git log --all --name-only | grep gateway  → چیزی نیست
آپلودهای این جلسه: فقط سه سند DOCX/MD اولیه
```

لطفاً **دقیقاً همان فایل** `tecteb-gateway-reference.zip` را دوباره ارسال
کنید. با آن این کارها انجام می‌شود و بدون آن هیچ‌کدام: خواندن قرارداد واقعی
API دروازه، نوشتن Adapter در برابر همان قرارداد، و تعیین اینکه آیا اتصال
مستند به ورود موجود (بند ۴٫۱ گزینه ۲) اصلاً وجود دارد. تا آن زمان فقط
`NullProvider` هست و هیچ ورود موفقی نمی‌سازد.

### ۴٫۴ قفل ارسال در Alpha

قفل فاز ۱ سر جایش می‌ماند: در نسخه آزمایشی هیچ پیامک/ایمیل/پرداختی از خود
افزونه ارسال نمی‌شود و هیچ گزینه‌ای این قفل را باز نمی‌کند. دعوت پرسنل ساخته
می‌شود اما ارسال نمی‌شود و وضعیت `pending_activation` می‌ماند.

## ۵. معماری

### ۵٫۱ جای منطق فروشنده

```
src/Modules/Vendor/
  Domain/          موجودیت‌ها، ماشین وضعیت، قواعد — PHP خالص
  Application/     use caseها: SubmitApplication، ReviewApplication، InviteStaff
  Infrastructure/  Repository روی wpdb، Adapterهای وردپرس، ذخیره‌ساز فایل
  Presentation/    مسیر و پوسته داشبورد فروشنده، فرم درخواست، صف بررسی مدیر
```

`Core/` **حداقلی می‌ماند**: فقط چیزهایی که چند ماژول مشترکاً لازم دارند
(container، migration runner، audit، تنظیمات، ساعت). هیچ کلاس Vendor در
`Core/` نوشته نمی‌شود. آزمون معماری موجود، نبود فراخوان WordPress در
`Core/`، `Contracts/`، `Domain/` و `Application/` را اجرا می‌کند و برای ماژول
تازه هم همان قاعده است.

### ۵٫۲ AuthenticationBridge

```php
// src/Contracts/Auth/AuthenticationBridgeInterface.php  — قرارداد مستقل
interface AuthenticationBridgeInterface {
    public function currentUserId(): ?int;                  // کیست؛ بدون دانستن وردپرس
    public function isLoggedIn(): bool;
    public function identityFor(int $userId): VendorIdentity; // شماره، وضعیت تأیید
}
```

پیاده‌سازی وردپرسی آن **فقط** در
`src/Modules/Vendor/Infrastructure/WordPress/WpAuthenticationBridge.php` است و
تنها جایی است که `wp_get_current_user()` و امثال آن صدا زده می‌شود. Domain و
Application فقط قرارداد را می‌بینند، پس آزمون واحدشان بدون وردپرس اجرا می‌شود
— دقیقاً مثل بقیه فاز ۱.

### ۵٫۳ نقش‌های موجود دست‌نخورده می‌مانند

| قاعده | جزئیات |
|---|---|
| هیچ نقشی حذف یا بازنویسی نمی‌شود | نه `administrator`، نه نقش‌های دکان (`seller`، `vendor_staff` و هر نام دیگری که روی سایت هست)، نه نقش‌های ووکامرس |
| فقط **افزودن** | یک نقش تازه `tmc_vendor` ساخته می‌شود و capabilityهای `tmc_*` فقط به همان و به `administrator` اضافه می‌شوند |
| کاربر چندنقشی | اگر کاربری از قبل نقش دکان دارد، نقش تازه **اضافه** می‌شود؛ چیزی از او گرفته نمی‌شود |
| بازگشت‌پذیری | غیرفعال‌سازی افزونه هیچ نقشی را حذف نمی‌کند؛ همان قاعده فاز ۱ که `uninstall.php` هیچ داده‌ای پاک نمی‌کند |
| آزمون | یک آزمون، فهرست نقش‌ها و capabilityهای قبل و بعد از فعال‌سازی را مقایسه می‌کند و هر حذف یا تغییر را شکست می‌داند |

## ۶. داشبورد فروشنده — مسیر و پوسته جدا

| موضوع | تصمیم |
|---|---|
| مسیر | جلوی سایت، زیر `/vendor/...` (rewrite endpoint اختصاصی افزونه). **نه** `/wp-admin/` |
| پوسته | پوسته اختصاصی فروشنده: هدر برند، ناوبری فروشنده، محتوای تک‌ستونی موبایل‌محور. منوی مدیریت وردپرس در آن نیست |
| دسترسی wp-admin | فروشنده به wp-admin نیازی ندارد؛ اگر وردپرس او را به wp-admin برد، رفتار پیش‌فرض وردپرس تغییر داده نمی‌شود مگر مالک بخواهد (تصمیم باز، بند ۹) |
| توکن‌های دیداری | همان توکن‌های برند فاز ۱ (رنگ‌ها، تایپوگرافی، فاصله‌ها) تا دو ناحیه یک محصول به‌نظر برسند |
| چیدمان | همان قاعده ADR-006: `@container`، بدون جعبه متن خفه‌شده |
| **آزمون پذیرش** | **مستقل.** آزمون‌های چهار صفحه مدیر هیچ چیزی درباره این ناحیه ثابت نمی‌کنند. برای داشبورد فروشنده: بررسی viewport/axe/کیبورد روی **مسیر خودش**، آزمون نقش و مالکیت (فروشنده A نباید داده B را ببیند)، و آزمون حالت‌های خالی |

پیش‌نمایش امروز تحویل شده است (بالا). هرچه در آن تصویر عدد یا نام است، ساختگی
و برچسب‌دار است؛ هیچ‌کدام از آن صفحه‌ها هنوز کد ندارند.

## ۷. مدارک خصوصی — ذخیره و تحویل

| موضوع | تصمیم |
|---|---|
| محل ذخیره | خارج از مسیر عمومی رسانه‌ها: `wp-content/uploads/tmc-private/<vendor>/…` با نام فایل تصادفی (`hash` ۳۲ نویسه‌ای) و بدون پسوند قابل‌حدس؛ مسیر واقعی فقط در جدول `tmc_vendor_documents` است |
| سد اول | فایل `.htaccess` با `Require all denied` و `web.config` معادل در همان پوشه |
| سد دوم (اصلی) | **هیچ فایلی مستقیم سرو نمی‌شود.** تحویل فقط از یک endpoint احراز هویت‌شده: `?tmc_doc=<id>&_wpnonce=…` که پیش از خواندن فایل، capability و **مالکیت** را بررسی می‌کند و سپس stream می‌کند |
| چرا دو سد | روی nginx فایل `.htaccess` خوانده نمی‌شود. سد اول کمک است، نه تکیه‌گاه؛ کنترل واقعی همان بررسی سمت سرور است |
| سرآیندها | `Content-Disposition: attachment`، `X-Content-Type-Options: nosniff`، `Cache-Control: private, no-store` |
| مجوز مشاهده | فروشنده مالک، پرسنل با مجوز صریح، و مدیر با `tmc_review_vendor`. هر دانلود در audit ثبت می‌شود (چه کسی، چه مدرکی، کِی) |
| جلوگیری از دسترسی متقابل | شناسه مدرک با `vendor_id` تطبیق داده می‌شود؛ تغییر id در URL به ۴۰۳ می‌رسد، نه به فایل. آزمون AC-PRIV دقیقاً همین را می‌سنجد |
| نوع فایل | فهرست سفید MIME + پسوند (پیش‌فرض پیشنهادی: `pdf`, `jpg`, `png`) با بررسی محتوا (`finfo`)، نه فقط پسوند؛ فهرست نهایی در همان فرم‌ساز بند ۲ قابل تنظیم است |
| اندازه | سقف پیش‌فرض پیشنهادی **۵ مگابایت** برای هر فایل، قابل تنظیم؛ سقف واقعی سرور (`upload_max_filesize`) خوانده و در UI نمایش داده می‌شود |
| حذف | حذف نرم؛ فایل تا تصمیم مدیر باقی می‌ماند و `uninstall.php` طبق قاعده فاز ۱ چیزی پاک نمی‌کند |

## ۱۰. وضعیت محیط — شاهد مالک در برابر آزمون ما

آنچه ما آزموده‌ایم: همان نسخه‌ها روی WordPress یکبارمصرف خودمان با PHP
**8.1.32** (نه 8.1.34)، و از این دور به بعد **هر سه حالت HPOS** به‌صورت واقعی
(گیت G-07): `hpos-sync-on` (1/1)، `hpos-sync-off` (1/0) و `legacy` (0/0). در هر
سه حالت افزونه خطا نداد و صفحه سلامت همان وضعیت مؤثر را گزارش کرد، در حالی که
«HPOS آزموده‌شده» همچنان **نامشخص** می‌ماند — چون اعلام سازگاری ادعای آزمون
نیست.

## ۱۱. قواعدی که این بخش حق شکستنشان را ندارد

- مرز Core و آزمون معماری (بند ۵٫۱).
- هر عملیات حساس: nonce + capability + اعتبارسنجی ورودی + ثبت رویداد (مادر ۲).
- مالی با عدد صحیح مقیاس‌دار، بدون float (FIN-01).
- خروجی‌های افزونه در Alpha بسته می‌مانند (بند ۴٫۴).
- CSS و JS فقط روی صفحات خود افزونه (گیت G-08) — برای ناحیه فروشنده هم همین:
  دارایی‌ها فقط روی مسیر `/vendor/` بار می‌شوند.
- اعلان‌های امنیتی و مدیریتی سایر افزونه‌ها پنهان یا حذف نمی‌شوند.
- نقش‌های موجود کاربران، از جمله نقش‌های دکان و مدیرکل، تغییر نمی‌کنند.
