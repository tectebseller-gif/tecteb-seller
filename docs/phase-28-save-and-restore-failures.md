# فاز ۲۸ — نوشتنی که انجام نشد، و بازگرداندنی که ادعا شد

**نسخه:** `0.1.0-alpha.31` · **ساختار داده: ۱۹ — هیچ migration ای اضافه نشد.**
سنجیده‌شده، نه فرض: `SchemaVersion::TARGET` همان ۱۹ است و در این نوبت هیچ فایلی
زیر `src/Core/Migration/` و `src/Modules/*/Infrastructure/Migrations/` عوض نشده.

`alpha.30` مسیر تأیید را وادار کرد جوابِ **فروشگاه** را بخواند. مالک سه جوابِ
دیگر را نشان داد که هنوز خوانده نمی‌شد — این بار همه در سمت **نوشتن**:

۱. `approveRevision()` خروجی `saveSpecs()` و `saveImages()` را نمی‌خواند.
۲. `restoreProduct()` سه بار می‌نوشت و هیچ‌کدام را نمی‌سنجید، پس پیام
   «محصول به حالت قبل برگشت» جمله‌ای بود که کسی بررسی‌اش نکرده بود.
۳. `DbProductRepository::saveImages()` نتیجهٔ `DELETE` را دور می‌ریخت.

دامنهٔ این دور همین مسیر ذخیره و بازیابی است. `alpha.30` و بسته‌های قبلی
**بازسازی یا جایگزین نشدند**.

---

## ۱. مورد ۳ اول، چون بدترینِ سه‌تاست

### آنچه اندازه‌گیری شد

`saveImages()` یک **جایگزینی** است: یک `DELETE` و یک ردیف به‌ازای هر تصویر. اگر
`DELETE` شکست بخورد و کسی نپرسد، درج‌ها ادامه می‌دهند و محصول هم تصویرهای قبلی
را دارد و هم تازه‌ها — با `sort_order`های **مشترک**، پس حتی «کدام اول است» قابل
پیش‌بینی نیست. و متد `true` برمی‌گرداند.

روی MariaDB واقعی، با گالریِ `[811, 812, 813]` و درخواست جایگزینی با
`[901, 902]` در حالی که `DELETE` رد می‌شود (خروجی خامِ اجرای بازتولید):

```
Array &0 [
     0 => 811,
-    1 => 812,
-    2 => 813,
+    1 => 901,
+    2 => 812,
+    3 => 902,
+    4 => 813,
 ]
```

پنج تصویر، درهم. و `saveImages()` گفت `true`.

و نیمهٔ دوم: اگر `DELETE` موفق شود و **درجِ دوم** شکست بخورد، `alpha.30` گالری
را با `[901, 903]` رها می‌کرد — تصویرهای قبلی رفته، لیست تازه ناقص — و درست
هم `false` برمی‌گرداند، ولی برای caller دیگر راهی نبود که بفهمد چه چیزی آنجا
مانده است.

### اصلاح

جایگزینی یک واحد کار است، و `DatabaseInterface` از `alpha.20` تراکنش دارد:

```php
if (!$this->db->begin()) { return false; }
if ($this->db->execute('DELETE …') === null) { $this->db->rollback(); return false; }
foreach (… ) { if ($written === null) { $this->db->rollback(); return false; } }
if ($main === null) { $this->db->rollback(); return false; }
return $this->db->commit();
```

هر گام با `null` سنجیده می‌شود، نه با «صفر یا کمتر»: **صفر ردیف یک موفقیت است**
(قاعدهٔ `alpha.8`) و محصولی که گالری‌اش از قبل خالی بوده چیزی برای حذف ندارد.

`saveSpecs()` هم همین را گرفت. آن یکی همیشه شکست را صادقانه گزارش می‌کرد، ولی
می‌توانست سه فیلد تازه و دو فیلد قدیمی را کنار هم رها کند و نسخهٔ schema را روی
همان مخلوط بالا ببرد — اندازه‌گیری‌شده: `material` تازه، `size` قدیمی، نسخه ۴.
کسی که می‌خواهد مقدارهای قبلی را برگرداند به‌قدر کافی کار دارد و نباید حدس بزند
کدام نیمه از قبل آنجاست.

**این در repository اصلاح شد، نه در caller** — «صرفاً افزودن بررسی در caller
کافی نیست»، و درست است: هیچ caller ای نمی‌توانست ببیند گالری درهم شده.

## ۲. مورد ۱ — دو نوشتنی که جوابشان خوانده نمی‌شد

`approveRevision()` جزئیات را با بررسی می‌نوشت و بعد مشخصات و تصویرها را **بدون**
بررسی. شکستِ مشخصات، سکوتِ کامل بود:

- محصول مشخصاتِ **قدیمی** خود را نگه می‌داشت؛
- `readiness` قبول می‌کرد — **چون همان مشخصات قدیمی همه سر جایشان بودند**؛
- projection بیرون می‌رفت، مبنا دربارهٔ همان مقدارها ثبت می‌شد، و نسخهٔ پیشنهادی
  `approved` می‌شد.

یعنی ویرایش فروشنده هرگز اتفاق نیفتاده بود و هر صفحه‌ای می‌گفت اتفاق افتاده.
اندازه‌گیری‌شده روی `alpha.30`: `code=revision_approved`.

حالا هر دو بررسی می‌شوند، **پیش از projection و پیش از ثبت تصمیم**، و نتیجه
`revision_write_failed` است با نام همان بخش. نسخهٔ پیشنهادی `pending` می‌ماند —
تنها وضعیتی که مدیر می‌تواند از آن دوباره تلاش کند — و مبنا تکان نمی‌خورد.

## ۳. مورد ۲ — بازگرداندنی که ادعا می‌شد

`restoreProduct()` سه نوشتن است روی دیتابیسی که همین حالا یکی از نوشتن‌ها را رد
کرده. `void` بودنش یعنی جملهٔ «محصول به حالت قبل برگشت» را هیچ‌کس نسنجیده بود.

حالا فهرست بخش‌هایی را برمی‌گرداند که **برنگشتند**، و هر سه فراخوان آن را
گزارش می‌کنند:

| مسیر | وقتی بازگرداندن موفق است | وقتی نیست |
|---|---|---|
| شکست نوشتنِ مشخصات/تصویرها | `revision_write_failed` + `restored=yes` | همان کد + `restored=no` + نام بخش |
| رد شدن `readiness` | همان `missing_image` / `missing_specs` قبلی | **`revision_not_restored`** با هر دو دلیل |
| شکست همگام‌سازی | `sync_failed` + `restored=yes` | `sync_failed` + `restored=no` + نام بخش |

و پیام‌ها این را می‌گویند. متنِ «چیزی نیمه‌کاره نمانده» فقط وقتی چاپ می‌شود که
واقعاً چیزی نیمه‌کاره نمانده باشد؛ وگرنه جمله می‌گوید **چه چیزی** برنگشت و
می‌خواهد همان محصول بررسی شود. آزمون، خودِ متن فارسی را می‌سنجد، نه فقط کد.

## ۴. آنچه اندازه‌گیری شد

### ۴٫۱ بازتولید روی `alpha.30`، و قبولی پس از اصلاح

رویشان اجرا می‌شوند. اسکریپت اگر بازتولید **قبول** شود خودش شکست می‌خورد.

همان‌جا دیده می‌شود نه سه اجرا بعد.

### ۴٫۲ چهار سناریو، و چیزی که در هر کدام سنجیده شد

`tests/Database/SaveAndRestoreFailureTest.php` روی **MariaDB واقعی**، با
`tests/Support/FailingDatabase.php`: هر statement به دیتابیس واقعی می‌رود جز
آن یکی که آزمون **نامش را می‌برد** (با شمارهٔ تکرار، تا نوشتنِ خودِ نسخهٔ
پیشنهادی از نوشتنِ **بازگرداندن** جدا شود). هیچ سناریویی فقط کد پیام را
assert نمی‌کند:

| سناریو | پروندهٔ بازارگاه | ووکامرس | نسخهٔ پیشنهادی | مبنا |
|---|---|---|---|---|
| مشخصات اختیاری ذخیره نشد | مشخصات و عنوانِ قبلی | دست‌نخورده (شمارش projection) | `pending` | تکان نخورد |
| `DELETE` گالری شکست خورد | `[811,812,813]` و تصویر اصلی ۸۱۱ | — | — | — |
| درجِ دومِ تصویر شکست خورد | همان سه تصویر، تصویر اصلی جابه‌جا نشده | — | — | — |
| بازگرداندن شکست خورد | عنوان برگشت، **گالری نه** | دست‌نخورده | `pending` | تکان نخورد |

سطر آخر همان چیزی است که این دور دربارهٔ آن است: وضعیتِ واقعی **نیمه‌برگشته**
است، و آزمون می‌سنجد که پیام همین را بگوید (`برگرداندن` و `تصویرها` در متن، و
نبودِ «چیزی نیمه‌کاره نمانده»).

همین بسته گرفته شد، نه روی بستهٔ قبلی.

### ۴٫۴ یک ایراد سازگاری که خودِ lint گرفت

اولین نسخهٔ پیام‌های تازه، سه ternary تودرتو داشت و
`PHPCompatibility --testVersion 8.1-` ردش کرد: «left-associativity … removed in
PHP 8.0». پرانتز راضی‌اش نکرد؛ درستش این بود که پیش‌فرض **داخل** همان closure ای
برود که نام بخش‌ها را می‌سازد. روی ۸٫۴ چیزی دیده نمی‌شد — همان قاعدهٔ `alpha.7`.

## ۵. آنچه `Not Run` است

- **نصب روی `tecteb.com` یا `staging.tecteb.com`** — انجام نشده و در مجوز نیست.
- **Rank Math واقعی** و **کش صفحهٔ واقعی**.
- **ناهماهنگی شمارنده** (`alpha.29` بند ۷): این دور هم ۹ رفت‌وبرگشت سنجیده شد و
  بازتولید نشد. باز اعلام می‌شود، بسته نه.

  پوشش‌دهنده تزریق می‌شوند، روی MariaDB واقعی و با تراکنش‌های واقعی. تحمیل یک
  شکست `DELETE` روی خودِ وردپرس آزموده نشده و لازم هم نیست: هر دو مسیر از همان
  `DbProductRepository` می‌گذرند.
