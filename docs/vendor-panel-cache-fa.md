# پنل فروشنده و کش — آنچه افزونه انجام می‌دهد و آنچه از شما لازم است

> این سند دربارهٔ یک مشاهدهٔ مشخص است: در `alpha.25` تبِ «پیش‌نویس» سه محصول و
> تبِ «در انتظار بررسی» یک محصول نشان می‌داد، ولی بازگشت به `/vendor/products/`
> همهٔ شمارنده‌ها را صفر می‌کرد و افزودن `?tmc_check=2241` هر چهار محصول را
> برمی‌گرداند.

## ۱. علت هنوز **اثبات نشده** است

این را صریح می‌نویسیم چون خلافش وسوسه‌انگیز است: ما اصلاحی انجام داده‌ایم که
با نشانه‌ها می‌خواند، **ولی روی سایت شما چیزی اندازه‌گیری نکرده‌ایم** و این
اصلاح را «رفع قطعی» اعلام نمی‌کنیم.

آنچه **می‌دانیم** دو چیز است، و هر دو از خود کد می‌آید:

- `countsByStatus()` یک `SELECT status, COUNT(*) … GROUP BY status` است بدون
  transient، بدون object cache و بدون حافظهٔ داخلی. افزونه چیزی کهنه برای
  تحویل‌دادن ندارد.
- بازدیدکنندهٔ خارج‌شده به فرم ورود **هدایت** می‌شود، نه اینکه پنل خالی ببیند.

هیچ‌کدام از این دو مسیر نمی‌تواند آنچه روی صفحه بود را بسازد. و نشانهٔ
«پارامتر بی‌معنی، جواب درست» نشانهٔ **کشی است که روی نشانی کلید می‌خورد** —
بیرون از افزونه. ولی نشانه دلیل نیست.

آنچه **نمی‌دانیم**: کدام لایه. WP Rocket، LiteSpeed، کش میزبان، یا یک CDN.
برای پاسخ، بند ۴ را ببینید.

## ۲. افزونه از `alpha.26` چه می‌کند

`VendorCacheControl` روی `plugins_loaded` با اولویت ۱ اجرا می‌شود — زودترین
لحظه‌ای که یک افزونه می‌تواند حرف بزند — و اگر نشانی زیر `/vendor/` باشد:

| کار | برای چه چیزی |
| --- | --- |
| `DONOTCACHEPAGE`, `DONOTCACHEOBJECT`, `DONOTCACHEDB`, `DONOTMINIFY` | زبان مشترک WP Rocket، W3 Total Cache، WP Super Cache و چند افزونهٔ دیگر |
| `do_action('litespeed_control_set_nocache', …)` | LiteSpeed ثابت نمی‌خواند، action می‌خواند |
| `Cache-Control: private, no-store, no-cache, max-age=0, must-revalidate` | پراکسی و مرورگر |
| `Vary: Cookie` | تا پاسخِ یک کاربر به کاربر دیگر داده نشود |
| `rocket_cache_reject_uri`, `rocket_cache_reject_uri_prefixes`, `wp_super_cache_rejected_uris`, `w3tc_can_cache` | فهرست «هرگز کش نکن» خودِ آن افزونه‌ها |

**دو چیزی که این کار نمی‌کند، و باید بدانید:**

1. **جلوی سرو شدن از کش را نمی‌گیرد.** `advanced-cache.php` **پیش از**
   بارگذاری هر افزونه‌ای اجرا می‌شود. تنها راه، فهرست reject خودِ آن افزونه
   است — که فیلترهای بالا پرش می‌کنند، ولی آن فیلترها وقتی خوانده می‌شوند که
   افزونهٔ کش پیکربندی‌اش را بازسازی کند (ذخیره یا پاک‌سازی).
2. **ورودی‌های کش‌شدهٔ قبلی را پاک نمی‌کند.** صفحه‌ای که پیش از نصب این نسخه
   ذخیره شده، تا وقتی یک بار پاک نشود همچنان سرو می‌شود.

پس بند ۳ کار **شماست** و یک‌بار لازم است.

## ۳. یک بار، پس از نصب `alpha.26`

### ۳-۱. WP Rocket

1. پیشخوان → **Settings → WP Rocket → Advanced Rules**.
2. در **Never Cache URL(s)** این دو خط را اضافه کنید:

   ```
   /vendor/(.*)
   /vendor/?$
   ```

3. **Save Changes** بزنید. همین ذخیره، فیلترهای افزونه را دوباره می‌خواند.
4. در نوار بالای پیشخوان: **WP Rocket → Clear cache**.
5. اگر Cloudflare از داخل WP Rocket وصل است: **WP Rocket → Settings → CDN →
   Cloudflare → Purge Cloudflare cache**.

### ۳-۲. LiteSpeed Cache

1. **LiteSpeed Cache → Cache → Excludes → Do Not Cache URIs**، همان دو الگو.
2. **LiteSpeed Cache → Toolbox → Purge All**.

### ۳-۳. کش میزبان (سی‌پنل، LiteSpeed سطح سرور، Varnish)

این لایه‌ها افزونه را نمی‌بینند و فقط سرصفحه‌ها را می‌خوانند. سرصفحهٔ
`Cache-Control: no-store` که از `alpha.26` فرستاده می‌شود برای بیشترشان کافی
است. اگر نبود، از میزبان بخواهید مسیر `/vendor/*` را از کش کنار بگذارد و یک
بار کش را پاک کند. **این کار را ما انجام نمی‌دهیم** و دسترسی‌اش را نداریم.

### ۳-۴. Cloudflare یا هر CDN جلویی

1. **Caching → Configuration → Purge Everything** یک بار.
2. **Rules → Page Rules** (یا Cache Rules): برای `*tecteb.com/vendor/*` مقدار
   **Cache Level: Bypass**.

## ۴. اگر باز هم تکرار شد — چه چیزی برای ما بفرستید

بدون این سه، هر تشخیصی حدس است:

1. **سرصفحه‌های پاسخ** یک بار روی صفحه‌ای که غلط است. در مرورگر:
   F12 → **Network** → صفحه را تازه کنید → اولین ردیف (`products/`) →
   **Headers** → بخش **Response Headers** را کامل عکس بگیرید.
   به‌ویژه این‌ها را می‌خوانیم: `x-rocket-cache`, `x-litespeed-cache`,
   `cf-cache-status`, `x-cache`, `age`, `cache-control`.
2. **آیا با کاربر دیگری هم همان اعداد را می‌بینید؟** اگر بله، پاسخِ یک نفر به
   نفر دیگر داده می‌شود و مسئله کش مشترک است، نه کش مرورگر.
3. **آیا در پنجرهٔ ناشناس (incognito) هم هست؟** اگر نه، کش خودِ مرورگر است و
   با `no-store` این نسخه باید بسته شود.

## ۵. آزمون پذیرشی که خودتان می‌توانید اجرا کنید

بدون هیچ پارامتر اضافی در نشانی:

| گام | انتظار |
| --- | --- |
| ۱. ورود به `/vendor/products/` | شمارندهٔ هر تب همان عددی باشد که فهرستش نشان می‌دهد |
| ۲. رفتن به تب «پیش‌نویس» و برگشتن به «همه» | هر دو عدد درست بماند |
| ۳. `F5` روی همان صفحه | عددها عوض نشوند |
| ۴. خروج و ورود دوباره | همان عددها، و **هیچ محصولی از حساب دیگر** |
| ۵. همان مسیر با حساب فروشندهٔ دوم | فقط محصول‌های خودش |

گام ۵ عمداً آخر است: اگر کشِ مشترکی باقی مانده باشد، دقیقاً اینجا خودش را
نشان می‌دهد و خطرش هم بیشتر از یک عدد غلط است.
