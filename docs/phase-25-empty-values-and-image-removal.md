# فاز ۲۵ — مقدار خالی، و حذف تصویر اصلی

**نسخه:** `0.1.0-alpha.28` · **ساختار داده:** ۱۸ (بدون تغییر، بدون migration)
· **دامنه:** دو نقصِ نام‌بردهٔ بررسی `alpha.27` و جلوگیری از بازگشت ایرادهای
قبلی. هیچ قابلیت تازه‌ای اضافه نشده است.

---

## ۰. خلاصه در یک پاراگراف

هر دو نقص یک شکل دارند: **مقداری که معنا داشت، به‌عنوان مقداری که معنا ندارد
خوانده می‌شد.** رشتهٔ خالی هم «پیشنهادی نیست» بود و هم «فروشنده می‌خواهد این
پاک شود»؛ صفرِ تصویر اصلی هم «تصویر اصلی ندارد» بود و هم «چیزی برای نوشتن
نیست». در هر دو مورد نتیجه یکی بود: افزونه گزارش می‌داد کاری را کرده که
نکرده بود. اصلاح در هر دو مورد این است که **وجود از مقدار جدا شود** — برای
پیشنهاد با `metadata_exists()`، و برای تصویر با نوشتنِ بی‌قیدوشرطِ همان مقدار
صفر.

---

## ۱. نقص اول — اعمال مقدار خالی در پذیرش پیشنهاد

### ۱٫۱ آنچه بود

```php
$pending = (string) get_post_meta($id, PENDING_PREFIX . $field, true);
if ($pending === '') { …مسیر «پیشنهادی نیست»… }
if ($pending !== '' && !self::writeField($wcProduct, $field, $pending)) {
    return false;
}
delete_post_meta($id, PENDING_PREFIX . $field);
```

`get_post_meta()` برای «ردیفی نیست» و برای «ردیفی هست و خالی است» **یک چیز**
برمی‌گرداند. پس فروشنده‌ای که توضیح کوتاهش را پاک کرده بود، پیشنهادش نامرئی
می‌شد؛ و وقتی مدیر «خواستهٔ فروشنده اعمال شود» را می‌زد:

1. `writeField()` اصلاً صدا زده نمی‌شد،
2. پیشنهاد **حذف** می‌شد،
3. مهر مالکیت از روی **متن قدیمی مدیر** نوشته می‌شد — یعنی متنِ مدیر به نام
   بازارگاه ثبت می‌شد،
4. و پیام «خواستهٔ فروشنده روی ووکامرس نشست» نمایش داده می‌شد.

اندازه‌گیری‌شده روی `alpha.27` نصب‌شده، پیش از هر اصلاحی:

```
stage=accept_empty_clears_the_field ok=false code=proposal_accepted
      storefront_len=55 really_empty=no pending_cleared=yes
```

۵۵ بایتِ متن مدیر سر جایش، پیشنهاد پاک‌شده، و کد `proposal_accepted`.

> **دقیق باشیم:** پس از آن کلیک، فیلد «مالِ بازارگاه» علامت می‌خورد، پس اگر
> بعداً **هر** چیزی محصول را دوباره projection می‌کرد، مقدار خالی بالاخره
> نوشته می‌شد. یعنی نتیجه به این بستگی داشت که چیز دیگری اتفاق بیفتد یا نه.
> برای محصولی که کسی دستش نمی‌زند، متن قدیمی برای همیشه می‌ماند — و در همهٔ
> حالت‌ها، صفحه در همان لحظه چیزی را «انجام‌شده» اعلام می‌کرد که نشده بود.

### ۱٫۲ آنچه هست

`StorefrontField` حالا `hasPending` را **حمل می‌کند** نه اینکه از مقدار
مشتقش کند، و `WooCommerceStorefrontFields::acceptProposal()`:

- وجود پیشنهاد را با `metadata_exists('post', $id, $key)` می‌پرسد؛
- مقدار خالی را برای فیلدهایی که `StorefrontField::mayBeEmpty()` اجازه
  می‌دهد **واقعاً می‌نویسد** (همه‌چیز جز `title`)؛
- عنوانِ خالی را با کد `title_required` رد می‌کند و **پیشنهاد را نگه
  می‌دارد**؛
- و فقط **پس از یک ذخیرهٔ سنجیده‌شده** پیشنهاد را پاک و مهر را ثبت می‌کند.

«ذخیرهٔ سنجیده‌شده» عمدی است: `WC_Product::save()` شناسهٔ محصول را برمی‌گرداند
— چه چیزی نوشته باشد چه نه — پس `save() > 0` هرگز نمی‌توانست موفقیت را از
شکست تشخیص دهد. حالا مقدار **دوباره خوانده می‌شود** و اگر با مقدار پیش از
نوشتن یکی باشد در حالی که چیز دیگری خواسته شده بود، این یک شکست است:

```php
if ($changes && fingerprint($after) === fingerprint($before)) {
    return 'storage_failed';     // پیشنهاد می‌ماند، مهری نوشته نمی‌شود
}
```

و **مسیر فیلد قدیمیِ بدون سابقه همین رفتار را دارد**: وقتی هیچ ردیف پیشنهادی
وجود ندارد، مقدار از پروندهٔ بازارگاه گرفته می‌شود — که ممکن است خالی باشد —
و همان قاعده‌ها روی آن اعمال می‌شود.

### ۱٫۳ رابط برگشتی عوض شد، و چرا

`acceptProposal()` از `bool` به `?string` رفت. دلیلش یک جمله است: «عنوان
نمی‌تواند خالی بماند» تصمیمی است که مدیر می‌تواند دربارهٔ آن کاری بکند، و
«ذخیره نشد» خطایی است که باید دوباره امتحان شود. `bool` هر دو را به یک جملهٔ
قرمز تبدیل می‌کرد.

## ۲. نقص دوم — اعمال حذف تصویر اصلی در مسیر همگام‌سازی

### ۲٫۱ آنچه بود

```php
if ($product->mainImageId > 0) {
    $p->set_image_id($product->mainImageId);
}
$p->set_gallery_image_ids(array_values(array_filter(
    $product->imageIds,
    static fn (int $id): bool => $id !== $product->mainImageId
)));
```

صفر هرگز به ووکامرس نمی‌رسید. و یک اثر جانبی که تا اجرای واقعی دیده نشد:
وقتی `mainImageId` صفر است، شرط `$id !== 0` **هیچ چیزی را فیلتر نمی‌کند**، پس
شناسهٔ تصویر اصلیِ قبلی هم در گالری ظاهر می‌شد **و هم‌زمان تصویر اصلی
می‌ماند**. اندازه‌گیری‌شده روی `alpha.27`:

```
was=main:4|gallery:17,18   →   now=main:4|gallery:4,17,18
featured_removed=no  first_gallery_picture_promoted=yes
```

### ۲٫۲ آنچه هست

```php
$images = StorefrontImages::of($product->mainImageId, $product->imageIds);
$p->set_image_id($images->main);          // بی‌قیدوشرط: صفر هم یک مقدار است
$p->set_gallery_image_ids($images->gallery);
```

سه چیز با هم:

- **`StorefrontImages`** همان شیئی است که مقایسه از آن ساخته می‌شود، پس
  «آنچه می‌خواهیم» و «آنچه می‌نویسیم» نمی‌توانند از هم جدا بیفتند. تا این
  نسخه یکی از آن دو فهرست را دستی فیلتر می‌کرد.
- **ترتیب گالری دست‌نخورده** می‌ماند؛ چیزی مرتب نمی‌شود.
- **هیچ تصویری خودکار بالا نمی‌آید.** ووکامرس جای خالی را با placeholder
  خودش پر می‌کند؛ گذاشتنِ تصویر بعدی به‌جای آن یعنی افزونه تصویر اصلی محصول
  کسی را خودش انتخاب کرده باشد.

### ۲٫۳ محافظت‌ها دست‌نخورده‌اند

`writeOwned()` عوض نشده. فیلد تصویرِ **ویرایش‌شدهٔ مدیر** `frozen` می‌ماند و
فیلد **بدون سابقه** `held` — یعنی حذف به‌عنوان پیشنهاد ثبت می‌شود و چیزی
نوشته نمی‌شود. هر دو در همین دور با سناریوی جدا سنجیده شدند.

## ۵. آنچه عمداً عوض **نشد**

- **مسیر «نسخهٔ ووکامرس بماند» (`keep`).** نقصِ گزارش‌شده دربارهٔ `accept` بود.
  `keep` مقدار ووکامرس را به پروندهٔ بازارگاه کپی می‌کند و اگر مدیر خودش
  عنوان را در ووکامرس خالی کرده باشد، پرونده هم خالی می‌شود — که همان «یک
  نسخه، نه دو نسخه» است، و `ProductReadiness` جلوی انتشارش را می‌گیرد.
  دست‌زدن به آن در این دور، تغییری بیرون از دامنهٔ خواسته‌شده بود.
- **`ManageProducts::cleanImages()`** هنوز وقتی تصویر اصلیِ انتخاب‌شده در
  فهرست نباشد، اولین تصویر را اصلی می‌کند. این قاعدهٔ **فرم فروشنده** است
  (کارت محصول باید تصویر داشته باشد)، نه قاعدهٔ مسیر همگام‌سازی. حالت «بدون
  تصویر اصلی» از دو راه واقعی به پرونده می‌رسد: حذف همهٔ تصویرها، و
  «نسخهٔ ووکامرس بماند» روی محصولی که مدیر تصویر اصلی‌اش را برداشته — و
  شواهد از همان `saveImages()` استفاده می‌کند که هر دو مسیر استفاده می‌کنند.

## ۶. قاعده‌های تازه

- **«موفق شد» را از خودِ داده بپرسید، نه از مقدار برگشتیِ save.**
  `WC_Product::save()` شناسهٔ محصول را برمی‌گرداند، چه چیزی نوشته باشد چه نه —
  همان‌طور که `WC_Order::save()` استثنای خودش را می‌بلعد (`alpha.11`). هر
  نوشتنی که تصمیمی به آن آویزان است باید **دوباره خوانده** شود.
- **وجود و مقدار دو پرسش‌اند، و `get_post_meta()` هر دو را با یک رشته جواب
  می‌دهد.** برای وجود `metadata_exists()` هست. این همان شکلِ «صفر و null» است
  که این مخزن در `alpha.8`، `alpha.11` و `alpha.13` دیده — این بار روی رشتهٔ
  خالی.
- **شرطی که یک مقدار را از نوشتن معاف می‌کند، آن مقدار را از سیستم حذف
  می‌کند.** `if ($x > 0) write($x)` یعنی صفر هرگز وجود نداشته است. اگر صفر یک
  حالت واقعی است، بی‌قیدوشرط بنویسیدش.
- **نسخهٔ قبلیِ نصب‌شده بهترین falsification است.** پیش از هر patch، همان
  شواهد روی `alpha.27` اجرا شد؛ شش مرحله شکست خورد. این از هر patchِ
  دست‌ساز قوی‌تر است، چون کدی که شکست می‌خورد همان کدی است که تحویل شده بود.
